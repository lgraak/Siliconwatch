## 2. Implementation details

- Python standard-library runner: deterministic matrix order, configurable individual cases, smoke and observer/output controls, sequential owned child processes, explicit time/disk budgets, inventory/binary checks, and retained incomplete results.
- Direct executable launch with `posix_spawn`; `wait4` is the sole child reaper and supplies user/system CPU and kernel child-lifetime RSS accounting. The Python runner's CPU is recorded separately.
- Bounded pipe capture to private local files, fixed-size read chunks, combined stdout/stderr cap, and timeout/interruption handling for the owned child process group. Raw hardware output stays in ignored `target/`.
- Periodic PID/start-time-checked RSS observations, preferring `smaps_rollup`, with an explicitly approximate VmRSS fallback. Missing reads remain null; methods are not silently mixed.
- Strict bounded table/JSON Lines parsing preserves scalar timing/status evidence, distinguishes complete output from a prefix, and validates schemas, sequence, scheduling arithmetic, and freshness fields.
- Reproducible Markdown from sanitized JSON; whole-run/post-warmup statistics, separate failed-scan distributions, ordinary medians, nearest-rank tails, and explicit observation counts. p95 requires 200 observations and p99 requires 1,000; these thresholds do not guarantee confidence.
- No Rust dependency, Python package, external service, performance setting, or application behavior change. Python 3.14.10 was used; the script API baseline is Python 3.11+, not independently tested on every supported Python version.

Important files: [runner](../../scripts/measure_overhead.py), [process accounting](../../scripts/overhead_process.py), [parsing/reporting](../../scripts/overhead_results.py), [provenance](../../scripts/overhead_provenance.py), five test modules under `scripts/tests/`, and [reproducibility commands](../benchmarks/README.md). The repository ignore file now excludes Python bytecode-cache directories. This report and the annotated historical proposal document the milestone.

**Explicit protocol deviations:** hard-bounded pipe-to-file capture replaces the proposed direct regular-file descriptor. Its draining/backpressure cost remains part of measurements; table output does not measure a terminal emulator. The kernel peak-RSS counter includes inherited launch high-water memory on this machine even with direct `posix_spawn`; it is retained with that scope, not presented as isolated application peak memory. Sampled RSS remains separate. No guessed launcher constant is subtracted.

## 6. Known issues, limitations, and risks

- Kernel child peak RSS is contaminated by inherited launch accounting, which may grow as the parent retains results. It cannot establish application-only peak memory or a Rust memory leak.
- Sampled RSS can miss transient peaks; its operational post-warmup window is not proof of allocator/thermal steady state. RSS reads and pipe capture perturb the workload.
- Parent-observed elapsed time includes setup, draining, and reap polling (up to approximately 50 ms polling delay), rather than exact kernel child lifetime. CPU accounting excludes the runner and does not cover total-machine or terminal-renderer CPU.
- Blocking kernel I/O can defeat prompt cancellation. SIGKILL/session teardown cannot guarantee final accounting. A persisted in-progress marker or output prefix is incomplete evidence.
- Thermal/frequency drift, background work, driver/page caches, filesystem behavior, suspend, correlated samples, and one-machine/provider coverage limit generalization. The load-average guard is coarse, not a thermal guarantee.
- No live fan readings, physical calibration, gaming frame times, terminal rendering, isolated-provider latency, root privileges, driver changes, or protective actions were tested or performed.
- The new Python tests have been run locally; the existing GitHub workflow is unchanged and does not yet invoke them.
- Table parsing follows the current experimental terminal format and must be reviewed if that format changes. Provider/category inventory comparison cannot detect an indistinguishable physical replacement. Exact settling duration and continuous thermal/background-process attribution were not measured.

## 8. Recommended next milestone

**Prototype 005: Provider-Level Sensor Latency Characterization**

**Proposal only — requires Chris's separate implementation and measurement approval. Nothing in Prototype 005 has been implemented or measured.**

**Objective:** characterize scan variability for individual exposed hwmon registrations and compare it with contemporary full scans. The observed 503.365 ms maximum and sustained 100 ms tails motivate investigation; the existing evidence does not identify their cause. A reproducible inconclusive result is acceptable.

### Proposed implementation and experiment

- Extend only the Python standard-library measurement tooling. Use the unchanged Rust 1.85.0 release executable and existing `--hwmon-root` option. A temporary local class directory contains symlinks to the selected existing registration; no files are created or changed in sysfs. First prove this selection method with fixtures.
- Treat a registration as the measured unit. Provider names can repeat: never combine registrations or select an arbitrary name match. Keep original source evidence available locally, use distinct sanitized run tokens in published results, and retain unsupported channels. Compare full-root and selected-root channel inventories; disclose changes to identity ambiguity caused by removing other registrations.
- Proposed initial bound: at most five currently exposed input-bearing registrations, selected and recorded before execution; three repetitions each, 301 attempts at 100 ms, JSON Lines with bounded pipe-to-file capture. Run a full-scan reference before and after each repetition block. Rotate provider order deterministically; run one child at a time with at least 15 seconds between cases. This is at most 21 measured cases, approximately 15.5 minutes before scan/output delays. Do not extend runs to chase an outlier.
- Use a 40-second per-case timeout and 25-minute suite budget, with the existing bounded termination/reaping behavior. Proposed caps are 8 MiB per captured case and 256 MiB per suite, including metadata reserve. Smoke-test the chosen inventory and project runtime/disk use before starting; stop if projections exceed those limits. Keep RSS observation disabled throughout this latency comparison, retaining child CPU accounting and its limitations.
- Record configuration, actual order/settling, binary and harness hashes, OS/kernel/CPU/toolchain, provider/category counts, output volume and observed background/power conditions. Retain failed or incomplete cases and their valid prefixes. A missing, unreadable, or changed selected registration is unavailable evidence, not a fast successful empty-provider scan; stop the comparison block without loading drivers or changing configuration.

### Timing, reporting, and interpretation

Preserve whole-run and ten-second post-warmup results. Report per-run scan duration, start lateness, start gaps, interval deviation, completed/failed attempts where validated, elapsed time, child CPU, median, maximum and observation counts. Use the existing p95 threshold of 200 observations and p99 threshold of 1,000; p99 will be unavailable in these short cases. Do not pool registrations or repetitions to manufacture tail eligibility.

Scan windows include discovery, identity work, sequential reads and any descheduling during that work; they are not pure driver or physical-sensor latency. Output occurs outside the scan window but can delay subsequent starts. Keep the same capture mode across comparisons and disclose varying output sizes and backpressure; no visible-terminal or exact output-cost attribution is claimed. Compare with full scans collected in the same experiment, using Prototype 004 only as historical context. Isolation changes fixed costs, ordering, caches and collision context: isolated times must not be summed or subtracted to infer full-scan provider contributions. Do not infer a causal explanation for the recorded maximum from a later correlation or its failure to recur.

### Acceptance criteria and expected tests

1. Reproducible commands, a bounded execution plan, sanitized machine-readable results and an offline-regenerable report distinguish observations, hypotheses and unknowns.
2. Deterministic fixtures cover exact registration selection, duplicate provider names, enumeration/renumbering, channel preservation, dangling/missing targets, permission failures, changed inventories and altered collision context. Unsafe or ambiguous selection fails explicitly.
3. Harness tests cover deterministic case order, full-scan controls, budgets, interruptions/cleanup, incomplete records, percentile eligibility and report regeneration; existing Rust and harness regressions pass.
4. Every attempted case is accounted for. No application behavior, sysfs settings, drivers, governors or thermal limits change. Unreproduced variability and unavailable attribution remain explicit.

**Risks and exclusions:** interactive workload/thermal drift, kernel caching, blocking reads, changed identity context and correlated samples limit inference. Five registrations may not be available; document exclusions without replacements selected after seeing results. No application optimization, daemon, scheduler change, adaptive polling, cache, database, API, GUI, alarm, hardware control or protective shutdown is included. Decision 43 remains pending. Approve or revise the proposed case/runtime/storage bounds before work begins; publication or merging of Prototype 004 does not authorize Prototype 005.
